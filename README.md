## Раздел 1. Введение. Повторение ООП-основ на Python (6/8/6)

**Теория:** классы и объекты; атрибуты экземпляра и класса; методы; `self`; конструктор `__init__`; инкапсуляция через `_` и `__`; свойства `@property`; наследование и `super()`; полиморфизм; магические методы (`__str__`, `__repr__`, `__eq__`); MRO; первичное сравнение композиции и наследования. Разбор типичных ошибок при переходе от процедурного кода к ООП.

**Практика:** рефакторинг простой текстовой игры в ООП-код. Выделение классов `Game`, `Player`, `Board`. Создание окна Pygame и каркаса игрового цикла. Первичная настройка структуры проекта и Git-репозитория. Задание — модуль 1 итогового проекта.

**Литература:** Лутц М. «Изучаем Python»; Калб И. «Object-Oriented Python».

## Раздел 2. Углублённое ООП на Python: протоколы, dataclasses, ABC (8/10/8)

**Теория:** абстрактные базовые классы (`abc.ABC`, `@abstractmethod`); `dataclasses` (`@dataclass`, `field`, `frozen`); протоколы (`typing.Protocol`); миксины; композиция vs наследование; `__slots__`; дескрипторы на базовом уровне; современные практики проектирования интерфейсов.

**Практика:** проектирование иерархии игровых сущностей: `GameObject` (ABC), `Movable`, `Drawable`, `Collidable`. Использование `dataclass` для конфигураций и компонентов. Написание миксина для логирования. Интеграция с Pygame Sprite. Задание — модуль 2 итогового проекта.

**Литература:** документация Python по `abc`, `dataclasses`, `typing`; Ramalho L. «Fluent Python».

---

## Раздел 3. Принципы SOLID и проектирование классов (8/10/8)

**Теория:** SRP, OCP, LSP, ISP, DIP. Применение SOLID к игровым системам. Принципы DRY, KISS. Рефакторинг «божественного объекта» (God Object) и «анемичной модели предметной области» (anemic domain model).

**Практика:** анализ плохого кода на примере монолитного класса `Game`. Рефакторинг с выделением ответственностей: `InputHandler`, `Renderer`, `Physics`, `GameState`. Применение инверсии зависимостей. Написание первых юнит-тестов. Задание — модуль 3 итогового проекта.

**Литература:** Martin R. C. «Clean Code»; Martin R. C. «Clean Architecture».

---

## Раздел 4. Паттерны: Game Loop, Update Method, Component (8/10/8)

**Теория:** Game Loop — классический и с фиксированным шагом; Update Method; Component; введение в ECS. Связь с Pygame: `clock.tick()`, обработка событий, обновление и отрисовка.

**Практика:** реализация игрового цикла Pygame с фиксированным шагом. Реализация `update()` для игровых объектов. Выделение компонентов `Health`, `Position`, `Velocity`. Простая компонентная система. Задание — модуль 4 итогового проекта.

**Литература:** Nystrom R. «Game Programming Patterns» (Game Loop, Update Method, Component); документация Pygame.

---

## Раздел 5. Паттерны: State, Strategy, Command (8/10/8)

**Теория:** State — управление состояниями игры и персонажей; Strategy — взаимозаменяемые алгоритмы; Command — инкапсуляция действий, отмена/повтор, макросы. Конечные автоматы (FSM).

**Практика:** FSM для игрового меню и AI врага. Стратегии оружия и движения. Команды управления игроком с возможностью undo. Задание — модуль 5 итогового проекта.

**Литература:** Nystrom R. «Game Programming Patterns»; Gamma E. et al. «Design Patterns».

---

## Раздел 6. Паттерны: Observer, Factory, Singleton (8/10/8)

**Теория:** Observer и EventBus; Factory (Simple Factory, Factory Method, Abstract Factory); Singleton и осторожность его применения. Примеры для игр: достижения, UI, создание врагов, менеджеры.

**Практика:** реализация EventBus через Observer. Фабрика врагов и предметов с разными характеристиками. Singleton для `AudioManager` и `Config`. Задание — модуль 6 итогового проекта.

**Литература:** Nystrom R. «Game Programming Patterns»; Gamma E. et al. «Design Patterns».

---

## Раздел 7. Архитектура игры: ECS, MVC, слоистая архитектура, базовые async/threading (8/10/8)

**Теория:** ECS и сравнение с классическим ООП; MVC/MVVM; слоистая архитектура (domain, application, infrastructure, presentation). Базовые многопоточность и асинхронность: `threading`, `Lock`, `Queue`, `asyncio`; сценарии использования — загрузка ассетов, фоновая музыка, простые сетевые заглушки. Ограничения и риски.

**Практика:** проектирование простой ECS для игровых сущностей. Разделение игры на слои. Асинхронная загрузка ассетов. Поток для фоновой задачи (например, музыка или логирование). Рефакторинг проекта под слоистую архитектуру. Задание — модуль 7 итогового проекта.

**Литература:** Nystrom R. «Game Programming Patterns»; документация Python по `threading`, `asyncio`; статьи об ECS.

**Практика:** написание тестов для игровых систем (позиция, здоровье, инвентарь). Рефакторинг проекта по результатам код-ревью с преподавателем. Подготовка демонстрации и презентации. Финализация итогового проекта. Задание — защита проекта.

## Итоговый проект

Итоговый проект — играбельный прототип на **Pygame**, демонстрирующий применение изученных принципов и паттернов. Выполняется индивидуально или в парах. Студенты выбирают тему из списка и адаптируют практические задания разделов под неё.

**Требования:**
- ООП как основная парадигма.
- Не менее 5 паттернов проектирования из изученных.
- Юнит-тесты для игровой логики.
- Читаемая структура кода (пакеты, модули).
- README с описанием архитектуры.
- Демонстрация + презентация (5–7 минут) + код-ревью с преподавателем.
- Допускается использование любых внешних ассетов.
- Базовое использование async/threading — по желанию, но приветствуется.

**Оценка:** промежуточные задания (модули 1–7) — 40%; финальный проект, защита и код-ревью — 60%.

## Приложение: рекомендации по адаптации проектов

**Общие рекомендации:**
- Каждый модуль курса добавляет в проект функциональность, соответствующую изученному паттерну.
- Если тема не позволяет напрямую применить паттерн, его адаптируют под предметную область.
- Рекомендуется вести журнал архитектурных решений (ADR).
- Использовать Pygame как основную библиотеку; для текстовых проектов допускается консольный ввод-вывод, но с сохранением ООП-архитектуры.

**Примеры адаптации:**

| Тема | Как адаптировать паттерны |
|---|---|
| Текстовая RPG | State — состояния персонажа; Command — действия в бою; Observer — события квестов |
| Космический шутер | Factory — враги; Component — здоровье, оружие, движение; Game Loop — цикл |
| Платформер | Strategy — типы прыжков; State — состояния игрока; Component — физика |
| Tower Defense | Factory — башни; Observer — волны; Strategy — цели башен |
| Симулятор фермы | Observer — рост растений; State — времена года; Command — действия |
| Головоломка | Strategy — алгоритмы решения; Component — ячейки; Singleton — менеджер уровней |
| Roguelike | Factory — генерация комнат; Component — характеристики; ECS — сущности |
| Карточная игра | Command — ходы; Strategy — AI; Observer — события карт |
| Аркадная игра | Game Loop — цикл; Update Method — движение; Component — коллизии |
| RTS | Factory — юниты; Observer — события; State — состояния юнитов |
| Визуальная новелла | State — ветки диалога; Command — выборы; Observer — флаги |
| Симулятор выживания | Component — голод, здоровье; Strategy — крафт; Observer — события |

**Критерии адаптации:** каждый модуль должен быть выполнен в контексте выбранной темы. Например, в разделе 4 студент реализует игровой цикл именно для своей игры; в разделе 6 — фабрику для объектов, специфичных для темы.
Ниже — дополнение к программе: задания для самостоятельной работы по каждому модулю и критерии их оценивания, а также критерии оценки итогового проекта. Самостоятельная работа распределена на 60 часов, предусмотренных программой.

## Общие критерии оценки самостоятельных работ

Каждая самостоятельная работа оценивается по 5-балльной шкале. Итоговая промежуточная оценка — среднее по модулям, переведённое в 40 баллов.

**Универсальные критерии:**
1. **Соответствие заданию** — выполнены все пункты, учтена тема проекта.
2. **Корректность и работоспособность** — код запускается, тесты проходят.
3. **Применение ООП, SOLID и паттернов** — решения обоснованы, а не формальны.
4. **Качество кода и структура** — читаемость, PEP8, модульность, Git-история.
5. **Тесты и документация** — наличие тестов, README, ADR, диаграмм.
6. **Своевременность** — сдача в срок; при задержке оценка снижается на 1 балл за каждую неделю.

**Для парных проектов:**  
Дополнительно учитывается вклад каждого участника. Если вклад неравномерный, преподаватель может скорректировать индивидуальные баллы в пределах ±10% от общей оценки.

**Шкала перевода в итоговую оценку:**
- 90–100 — отлично;
- 75–89 — хорошо;
- 60–74 — удовлетворительно;
- 0–59 — неудовлетворительно.

## Итоговое распределение баллов

- Модули 1–8 (практика + самостоятельная работа): **40 баллов**.
- Итоговый проект: **60 баллов**.
- **Всего: 100 баллов.**

При необходимости можно добавить бонусные баллы (до 5) за инициативу: дополнительные тесты, оптимизацию, нестандартное применение паттернов, вклад в код-ревью других студентов.
